# 统一时间线内存化设计

> 目标：把「shell 模式记录自己的、AI 模式记录自己的、组装上下文时再按时间混一次」的现状，改成**内存里就是一条按时间序的单一流**，shell 事件与 AI 对话从构造上就交织在同一条流里，组装时不再做时间归并。
>
> 状态：**设计稿（未实施）**。本文只描述方案与落地切法，不含代码改动。实施前须完成 §7「待确认项」的核对，尤其 §7.2（切换时两套真身不对称）。

## 1. 现状

内存里是**两套结构，各记各的**，组装请求时才按时间混排：

| 维度 | shell 侧 | AI 侧 |
|---|---|---|
| 载体 | `rec`（`session.Recorder`）内的 `[]ShellEvent` 环 | `active.hist`（`[]ctxMsg`） |
| 喂入时机 | shell 模式：`rec.Type/Enter/Output/Pause/Resume`（`main.go:1678-1693`、`2211-2248`） | 引擎返回后 `append`（`main.go:1613-1615`） |
| 保留策略 | 硬上限：环 `MaxEvents` 条 / 单条输出 `MaxOutput` / 单次请求上下文 `MaxContext` 总预算（`session.go:33-49`），超限折叠成占位（`foldShellEvents`，`main.go:2714`） | 整轮裁剪 `maxHistory` 条（`trimHistory`）+ checkpoint 压缩（`main.go:1600-1615`） |
| 真身来源 | **仅本进程活 pty**，不持久、切换不重建 | **从磁盘重建**：`readSessionHistory`→`reconstructHistory`（`session_cmds.go:351,374`），切换/启动时重载 |

**组装时再混**：`buildTimeline`（`main.go:2689`）用双指针按 `events[i].Time` vs `hist[j].ts` 归并成统一时间线，shell 事件各自成一条 `role:"shell"` 消息（`main.go:1501-1510`）。

**关键事实：磁盘日志已经是统一时间序单流。** `active.log` 是 `session.Record{Ts,Kind,P,Calls}` 的 JSONL（append-only），shell 记录（`shk`/`shl`）与 AI 记录（`usr`/`asw`/`tool`/`noti`/`sys`/`rea`）按写入顺序天然交错（`internal/session/log.go:96-106`，`Ts=time.Now().UnixNano()`）。

所以现状的「内存两套 + 组装再混」其实是：**一个采集结构（`rec`）+ 一个消费视图（`hist`），磁盘才是共同真身**。内存的拆分并非语义必需，而是采集与消费两条路径各自维护了一份。

## 2. 目标

内存即一条按时间序的 `[]event`，**单一真身**，每个元素是带 kind 的联合类型——**恰好就是磁盘的 `session.Record` 本身**（`Kind` 已是 `shk/shl/usr/asw/tool/...` 的联合）。这样：

- `buildTimeline` 的时间归并删除：流已有序，组装 = 顺序遍历 + 按 kind 套各自预算/映射。
- 显示（`renderUnifiedReplay`）与上下文组装消费**同一条流**，一个喂原始、一个喂映射，天然一致。
- 切换/启动重建 = 「把目标会话磁盘读进流」，`reconstructHistory` 退化为「load stream」。
- 用户指出的「两个列表再按时间混一次」从构造上消失。

## 3. 三个必须绕开的约束（当初会拆的原因）

统一流不是「一条流、一套裁剪」，而是「**一条流、两类元素、两套裁剪**」，且采集与提交要分离。逐条说明，均非阻塞，但决定了实现形态。

### 3.1 两条保留预算，按 kind 分治

- shell 元素走 8KB/20 条（超了折叠成一行占位，`foldShellEvents`）；
- AI 元素走整轮 `maxHistory`（`main.go:2577`）+ checkpoint 压缩。

统一流上按 kind 分支裁剪即可。结论：不会真的只剩一套逻辑，而是把两套裁剪**同置**到一条流上。实现上把「裁剪」抽成按 kind 的策略接口，避免 if/else 散落到组装各处。

### 3.2 压缩（compaction）是「改写前缀」，与 append-only 冲突

现在 `active.hist` 压缩时把前缀改写成 `CheckpointMessage`（`main.go:1600-1611`），而日志是 append-only。统一流里把压缩改成**游标 + 标记点**：

- 流本身只追加，绝不改写；
- 压缩 = 把「起点游标」推进到某条记录之后 + 在该位置追加一个 `checkpoint` 事件；
- 组装时跳过游标之前的记录，用 `checkpoint` 事件表示被压掉的前缀。

即：压缩从「就地改写」变为「移动读起点 + 追加标记」，与 append-only 一致。

### 3.3 shell 输出是流式/可变的

`rec.Output(chunk)` 边到边追加到「进行中的事件」，并做头尾截断（`session.go:413-455`）——这是对**末尾元素的 in-place 变异**，与不可变 append-only 略冲突。解法：

- 把「采集中的 in-progress 命令」留作一个小**工作缓冲区**（`rec` 降级为纯采集缓冲）；
- `Enter`/flush 时才把**已提交**事件 commit 进统一流。

即「采集（进行中）与记录（已提交）分离」：`rec` 只负责把按键/输出聚合成一条完整 shell 事件，commit 后该事件以 append 方式进流，之后不再变。

## 4. 设计细节

### 4.1 数据模型

统一流元素直接复用 `session.Record`（`Ts int64, Kind string, P string, Calls []RecordCall`）。无需新类型——`Kind` 已是联合标签，`Record` 已同时承载 shell（`shk`/`shl`）与 AI（`usr`/`asw`/`tool`/`noti`/`sys`）两类。内存流即 `[]session.Record`（append-only，`writeMu` 保护）。

### 4.2 采集/记录分离

- `rec`（`session.Recorder`）保留为**进行中采集缓冲**：继续 `Type/Enter/Output/Pause/Resume`，但不再维护自己的 `[]ShellEvent` 环，改为在 `Enter` 时向统一流 **commit** 一条 `shk` 记录 + 其 `shl` 输出记录。
- 进行中的输出截断（head/tail、`MaxOutput`）仍在 `rec` 内完成，commit 时输出已是终态。
- AI 侧（`usr`/`asw`/`tool`/`noti`/`sys`）由现有 `logWrite`/`logWriteRec` 路径 commit 进同一流。

### 4.3 组装 = 顺序遍历（`buildTimeline` 删除）

组装请求时不再做双指针时间归并。顺序遍历流：

- `shk`/`shl` → 套 shell 预算（`foldShellEvents` 语义），渲染为 `role:"shell"` 消息；
- `usr`/`asw`/`tool` → 套 AI 整轮语义（游标起点之后），映射为 `user`/`assistant`/`tool` 消息；
- `checkpoint` → 表示被压缩的前缀，映射为 `CheckpointMessage`。

顺序遍历天然保序，`buildTimeline` 与 `ts` 并列的 tie-break（`main.go:2696`）一并消失。

### 4.4 显示 = 顺序遍历同一流

`renderUnifiedReplay`（`session_cmds.go:485`）改为直接顺序遍历内存流（当前已是从磁盘 `ReadMessages` 读再渲染），与组装共用一条流，不再各读各的。

### 4.5 加载/切换 = 读流

切换/启动时把目标会话磁盘日志读进统一流（`readHistory` 的 `reconstructHistory` 退化为「load stream」，`session_cmds.go:351`）。`active.hist` 不再是独立真身，而是流上「AI 子集 + 游标」的**投影**（或直接由流组装）。

### 4.6 生命周期

`rec` 当前是进程级单例，切换会话时**不重建**（仅退出时 `rec.Abort()`，`main.go:1091`），而 `active.hist` 切换时会从磁盘重建。统一后，切换 = 「从目标会话磁盘 load 流 + 重置 `rec` 采集缓冲」，顺带把旧 shell 事件清掉（见 §7.2，这是修复，须先核对 `rec` 与 pty 代的生命周期）。

## 5. 不变量与安全前提

- 模式串行：shell 与 AI 不并行，所有 append 在 `writeMu` 下进行，流**天然严格有序**，无需排序，`ts` 并列的 tie-break 从构造上消失。这是统一后「顺序遍历即可」的安全前提。
- 流 append-only：唯一变异是末尾 in-progress 缓冲（§3.3），commit 后不可变。
- 压缩不改写流，只移动游标 + 追加 `checkpoint`（§3.2）。

## 6. 收益

- 单一真身：内存流 == 磁盘形态（`[]session.Record`），无「内存一套、磁盘一套、加载再拼」的三方一致问题。
- `buildTimeline` 时间归并删除，`reconstructHistory` 简化为 load。
- 显示与上下文组装共用一条流，天然一致。
- 用户指出的「两个列表再按时间混一次」从构造上消失。

## 7. 风险与待确认项（实施前必须核对）

### 7.1 压缩游标要覆盖整轮语义

压缩游标 + `checkpoint` 方案须完整覆盖 `trimHistory` 的整轮语义（`main.go:2745`）：一次裁剪要移除「user + 其 assistant + 紧随的 tool 结果」整轮，**不得把 tool 结果与 assistant 拆散**。游标推进点必须落在轮边界。

### 7.2 切换时两套真身不对称（重点，已核对代码）

现状确认：`rec` 是进程级单例（`main.go:330` `rec := session.New()`），退出时才 `rec.Abort()`（`main.go:1091`）；`switchToMeta`（`main.go:1830`）kill 当前 shell、在同一 pty 上重启新 shell、重绘、重置每会话状态，但**不触碰 `rec`**，而 `active.hist` 在切换/启动时从磁盘重建（`main.go:1095,1943`）。即：切换后 `rec` 的 shell 事件环**跨会话残留**，`active.hist` 却已换成目标会话——两套真身不同步，旧会话的 shell 命令仍会进入新会话的 AI 上下文。统一成「从目标会话磁盘 load 流 + 重置 `rec` 采集缓冲」顺带修复此问题，但须确认 `rec` 重置与 pty 代切换（`switchToMeta` 的 shell kill/wait/restart）的时序：在 shell 重启前/后重置 `rec`，避免切换瞬间的退出重绘被归属到某条命令，或旧 in-progress 事件混入。

### 7.3 `rec` 输出截断与流提交边界

`rec.Output` 的 head/tail 截断（`session.go:413-455`）须在 commit 前完成，确保进流的是终态输出；`Pause`（全屏）期间不 commit，`Resume` 后的退出重绘不归属任何命令（维持现契约）。

## 8. 落地切法（小步）

1. **Phase 1 — 内存活镜像**：统一流做成磁盘 append 时同步进内存的活镜像（`[]session.Record`）；组装改为「顺序遍历 + 按 kind 预算」，删除 `buildTimeline` 时间归并；显示与组装共用该流。此时 `rec` 暂仍维护自己的环（双写），验证组装/显示与旧行为等价。
2. **Phase 2 — 拆 `rec`**：`rec` 降级为「进行中采集缓冲 + commit 进流」，去掉独立环；`Enter`/flush commit `shk`+`shl`。
3. **Phase 3 — 压缩改游标**：压缩从「就地改写 `active.hist`」改为「游标 + `checkpoint` 事件」，`active.hist` 退化为流上投影。

每阶段以 `TestInterleavedShellAndAITimeline`（`cmd/rysh/integration_test.go:2692`）为回归基线：前置命令 → AI Q1 → 中间命令 → AI Q2，断言 Q2 请求体按 `[前缀, $BEFORE, user Q1, assistant R1, $MID, user Q2]` 严格时序。
