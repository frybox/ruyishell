# Agent Harness 上下文管理对比分析

> 研究对象：`~/research/harness/` 下的 pi、codex、opencode、grok-build、deepseek-harness（dsh）。
> 分析日期：2026-08-28。所有结论均带源码位置，可复查。
> 写作动机：一个 9 小时任务陷入「上下文变重 → 压缩 → 忘了要干嘛 → 读文件重新定位 → 上下文又变重」的循环。上下文管理是 ruyishell 未来的核心，本文档把五个 harness 的机制拆清楚，给出对本项目的启示。

---

## 0. 先把病症拆清楚

9 小时循环的四个环节，每个环节对应一类机制缺失：

| 环节 | 病因 | 对治机制（下文中各 harness 的做法） |
|---|---|---|
| ① 上下文变重 | 工具输出（read/bash 的大输出）无治理，全量入上下文 | 源头截断、spill 到文件、旧工具输出 prune |
| ② 压缩后忘了要干嘛 | 摘要是"叙述性复述"，没有目标字段；原始用户消息被丢弃 | 结构化 checkpoint（Goal 是一级字段）、保留原始 user message、重注入 mission |
| ③ 读文件重新定位 | 摘要不记录"已读/已改过哪些文件"，模型只能重读重建认知 | 累计文件清单（read/modified files）随 checkpoint 传递 |
| ④ 重读后又变重 → 回到 ① | 新的大输出再次入上下文；且没有任何"当前状态"锚点 | 源头治理（同①）+ 压缩后重注入 todo/子任务/后台任务等**存活状态快照** |

**关键洞察**：压缩（compaction）不是"把历史弄短"，而是**状态交接（handoff）**——把"目标、进度、决策、已知文件、当前存活状态"无损地移交给一个没有参与过对话的新模型。凡是把压缩当"截断+摘要"的，都会掉进②③；凡是只治理①不管②③④的，循环只是变长不会消失。

## 1. pi：文件即上下文 + 自包含 checkpoint

pi（earendil-works/pi-mono，Mario Zechner 项目）是五个里设计哲学最"偏"的，特色也最多出在这里。注意它有两代代码：`packages/coding-agent/src/core/`（当前产品路径）和 `packages/agent/src/harness/`（新 v4 持久化运行时的实现+设计规范文档 `packages/agent/docs/harness.md`）。下述机制在两条路径上都成立。

### 1.1 极简系统提示词 + 渐进披露（progressive disclosure）

`packages/coding-agent/src/core/system-prompt.ts` 的 `buildSystemPrompt` 生成的固定提示词只有几百 token：

- 一句话角色："You are an expert coding assistant operating inside pi, a coding agent harness."
- 工具清单：每个工具**一行** snippet
- 几条 guidelines
- **pi 自身文档只给路径**："Pi documentation (read only when the user asks about pi itself...)" + readme/docs/examples 的绝对路径
- 项目指令（AGENTS.md 等）包在 `<project_context>` 里
- 当前工作目录

特色在于：**所有知识默认在磁盘上，上下文里只有指针**。pi 自己的文档、skills、项目指令，都是"需要时模型自己去 read"。对比 grok-build 把 6-7k token 的工具说明书写死在系统提示词里，这是两个极端。

skills 的加载（`packages/agent/src/harness/system-prompt.ts`）是典型：

```
The following skills provide specialized instructions for specific tasks.
Read the full skill file when the task matches its description.
<available_skills>
  <skill><name>..</name><description>..</description><location>path/SKILL.md</location></skill>
</available_skills>
```

只有 name/description/location 进上下文，正文靠模型按需读取。项目指令加载优先级（`core/resource-loader.ts`）：`AGENTS.override.md > AGENTS.md > CLAUDE.md`，沿目录祖先向上收集，另有全局层。

### 1.2 会话是树，压缩是自包含 checkpoint

`packages/agent/src/harness/session/context.ts` 的 `defaultContextEntryTransform` 只有 10 行：找到**最近一个 compaction entry**，上下文 = `[compaction] + 其后所有 entry`，更早的**永不读**（"Context never reads past a compaction"）。compaction entry 自带 `summary + retainedTail + tokensBefore`，是一个自包含的快照点，不是指向历史的指针。compaction entry 投影为一条 user 消息，前缀是 "The conversation history before this point was compacted into the following summary: `<summary>`..."（`harness/messages.ts`）。

会话本身是 `parentId` 链接的不可变 entry 树（message / compaction / branch_summary / custom 四种 entry），支持 `/tree` 分支导航；导航时可选做 **branch summarization**（把放弃的分支摘要注入新分支）。新 v4 设计文档（harness.md）进一步把它做成持久化运行时：三个存储（write-once entries / mutable registers / append-only usage ledger）、原子事务、`op.state` 持久化程序计数器、effect sandwich 崩溃恢复——压缩、导航都是可恢复的"操作"。这部分目前主要在设计+部分实现阶段。

### 1.3 结构化 checkpoint 摘要（治"忘了要干嘛"的核心）

`packages/agent/src/harness/compaction/compaction.ts` 的 `SUMMARIZATION_PROMPT` 强制固定格式：

```markdown
## Goal
[What is the user trying to accomplish? Can be multiple items...]
## Constraints & Preferences
## Progress
### Done / ### In Progress / ### Blocked
## Key Decisions
## Next Steps
## Critical Context
```

外加由 harness 机械提取（不靠模型回忆）追加的：

```
<read-files>
path/to/file1.ts
</read-files>
<modified-files>
path/to/changed.ts
</modified-files>
```

**文件清单是累计的**：`extractFileOperations` 从待压缩消息的工具调用中提取 read/edit 文件，再合并**上一次 compaction entry 的 `details`**（`readFiles/modifiedFiles`），逐代累积。压缩后模型知道"我已经读过这 23 个文件、改过这 4 个"，不需要重读来重建认知——这是对循环环节 ③ 最直接的解法。

### 1.4 迭代式摘要更新（不是重新摘要最近一段）

第二次压缩时，`UPDATE_SUMMARIZATION_PROMPT` 接管：旧摘要放 `<previous-summary>`，规则是 "PRESERVE all existing information ... MOVE items from In Progress to Done ... If something is no longer relevant, you may remove it"。摘要是一份**持续更新的状态文档**，Goal 从第一次压缩后就一直住在里面，不会因为"只摘要最近一段"而丢失。

### 1.5 切分、阈值与恢复

- 切点规则（`findValidCutPoints`）：**永不在 toolResult 处切**（必须和它的 tool call 在一起）；优先 turn 边界；单个 turn 超过保留预算时做 split turn，给 turn 前缀单独生成一份 "Original Request / Early Progress / Context for Suffix" 摘要再合并。
- 阈值（`shouldCompact`）：`contextTokens > contextWindow - reserveTokens`（reserve 默认 16k）；保留 `keepRecentTokens` 默认 20k。
- token 估算（`estimateContextTokens`）：**provider 实际 usage 为基准 + 尾部消息 char/4 启发式**，不用纯估算、也不依赖本地 tokenizer。
- 溢出恢复（`agent-session.ts` `_checkCompaction`）：响应因上下文溢出报错时，**删掉失败的那条 assistant 消息 → 压缩 → 重试一次**（`_overflowRecoveryAttempted` 防无限循环）；还有对"压缩前 stale usage 误触发"的防抖处理。
- 摘要请求本身：独立 session id、`cacheRetention: "none"`（一次性请求不污染 prompt cache）。
- 可扩展：`session_before_compact` 钩子可取消/替换摘要（比如换便宜模型做摘要）。

### 1.6 源头截断

`core/tools/truncate.ts`：工具输出默认 **2000 行 / 50KB** 双限，read 从头截、bash 从尾截（错误在末尾）、grep 单行 500 字符，截断带元数据（总行数/总字节/截断方式）告知模型。

### pi 的优劣

**优**：
1. "文件即上下文"把固定开销压到最小，前缀极稳，KV cache 友好；
2. 压缩 = 自包含 checkpoint，上下文投影是一个 10 行纯函数，可推理、可测试；
3. 结构化 checkpoint + 累计文件清单，正面解决"忘目标 + 重读文件"；
4. 迭代式摘要更新保证 Goal 跨多次压缩存活；
5. 新 v4 的持久化设计把压缩/崩溃恢复/分支做成了工程上严格的问题（原子事务、可枚举崩溃态）。

**劣**：
1. 原始用户消息**不保留原文**（只靠摘要的 Goal 段 + retainedTail），摘要质量差时 Goal 会漂；
2. 极简系统提示词对模型的自主性要求高——弱模型不知道去 read 文档、read skill，能力直接打折；
3. 没有压缩后"存活状态快照"（在跑的后台任务/子任务）的机制——靠 retainedTail 里恰好有相关内容；
4. 无独立 token 计量服务，阈值判断嵌在 agent-session 里，且"char/4"对中文/代码偏粗。

## 2. codex：上下文碎片生态 + 三级 token 预算

codex（OpenAI，`codex-rs/`，Rust）的上下文管理是五个里**最体系化但最封闭**的。核心思想：**没有"一次性系统提示词"，上下文是一组有类型、可重注入、可 diff 更新的碎片（ContextualUserFragment）**，全部作为 developer/user 消息注入对话。

### 2.1 碎片生态

`codex-rs/core/src/context/` 目录就是碎片的清单（40+ 种），几个关键的：

- `base_instructions`：模型基础指令，role = **developer** 消息（`client.rs` 中作为 prefix 注入，不是 Responses API 的 system 字段）；
- `user_instructions`：AGENTS.md，role = **user** 消息，带 `# AGENTS.md instructions ... </INSTRUCTIONS>` 标记；
- `environment_context`：cwd、git、文件系统权限、sandbox 配置；
- `current_time_reminder` / `time_reminder`：时间重新注入；
- `token_budget_context`：token 预算相关（见下）；
- `compaction_summary`：压缩摘要（role = user）；
- `model_switch_instructions`、`multi_agent_*`、`guardian_*`、`inter_agent_*` ...

每个碎片有 `content_kind`（如 `agents_md.instructions`）、role、标记，且实现 `WorldStateSection` 的碎片支持 **diff 重注入**（`world_state.rs` 的 `render_diff`）：状态变了只注入变化部分，没变不重复。

### 2.2 context window 是一等对象

`token_budget_context.rs`：每个压缩后的"窗口"有 `window_id / first_window_id / previous_window_id / window_number`，以 `<context_window>` 元数据注入对话——**模型被明确告知"你是第 N 个上下文窗口，你继承了前一个"**。另有 `thread_hint` 说明会话延续。

### 2.3 三级 token 预算

`session/token_budget.rs` + `session/context_window.rs`：

1. **正常**：`auto_compact_scope_tokens >= scope_limit + fallback_buffer` 时触发 auto-compact。scope 可配置（`model_auto_compact_token_limit_scope`），限额可来自模型目录（model-owned defaults）或用户配置，且会减去"窗口起始时已占用的 prefill tokens"；
2. **提醒**：剩余 tokens ≤ `reminder_threshold_tokens` 时，注入一条 developer 消息 `TokenBudgetReminder`（"You have {n} tokens left in this context window."）——**把预算显式告诉模型**，让模型自己收敛；
3. **兜底**：剩余 = 0 且无法再压缩时，注入 `AutoCompactFallbackPrompt`（收尾提示），让模型优雅结束而不是硬报错。

### 2.4 压缩后的历史：原文 user message 全保留

`compact.rs` 的 `build_compacted_history`：

```
[ 重注入的 initial context (AGENTS.md/env/permissions)
, 所有历史 user message —— 从新到旧选取，总预算 20k tokens（COMPACT_USER_MESSAGE_MAX_TOKENS），超了截断
, 摘要 —— 永远在最后 ]
```

要点：
- **原始用户消息逐字保留**（不是摘要里的转述）。这是五个 harness 里抗目标漂移最强的设计——用户说过的每句话（在 20k 预算内）压缩后原样在场；
- 摘要放最后，注释明说原因："the model is trained to see the compaction summary as the last item in history after mid-turn compaction"（模型训练时就是按这个布局看到的）；
- initial context 重注入位置有讲究（`insert_initial_context_before_last_real_user_or_summary`）：优先插在最后一条真实用户消息之前，保证摘要仍在末尾。

摘要提示词（`prompts/templates/compact/prompt.md`）很短："You are performing a CONTEXT CHECKPOINT COMPACTION. Create a handoff summary for another LLM that will resume the task." 摘要前缀（summary_prefix.md）："Another language model started to solve this problem and produced a summary of its thinking process. You also have access to the state of the tools that were used by that language model..."——交接话术。

### 2.5 其他

- **remote compaction**（`compact_remote*.rs`，含 v2 与 image budget）：摘要可以委托给服务端执行；
- **输出截断**：中间截断（保头保尾），带 "Warning: truncated output (original token count: X)"（`utils/output-truncation`）；
- **rollout budget**：线程级 token 预算 + 提醒，超了直接 `SessionBudgetExceeded`；
- 诚实的警示文案（`compact.rs`）："Heads up: Long threads and multiple compactions can cause the model to be less accurate. Start a new thread when possible to keep threads small and targeted."——官方承认多次压缩会掉智，对策是开新线程。

### codex 的优劣

**优**：
1. 原文 user message 保留 + initial context 重注入，抗漂移最稳；
2. 把 token 预算、窗口编号告知模型，模型有"自我收敛"的信息基础；
3. 碎片 + diff 重注入，上下文状态变更是增量、可审计的；
4. 三级降级（压缩→提醒→兜底收尾）覆盖完整。

**劣**：
1. 复杂度极高（compact 相关 10+ 文件、remote v1/v2），与 OpenAI 闭源生态（Responses API、模型目录里的 model-owned defaults）深度耦合，无法移植；
2. 20k 预算给"所有 user message"——一堆 "continue"、"好的" 也占预算，信噪比低；
3. 碎片全部前置注入，固定前缀比 pi 大得多，cache 收益依赖前缀稳定；
4. 没有文件清单累计、没有存活状态快照。

## 3. opencode：两级治理（prune/compact）+ 计划文件外置

opencode（SST，`packages/opencode`，TypeScript；新一代核心在 `packages/core`）。特色是**把"便宜的治理"和"昂贵的压缩"分成两级**，以及**计划文件外置**。

### 3.1 第一级：prune（无 LLM，免费）

`packages/opencode/src/session/compaction.ts` 的 `prune`：从新到旧遍历工具结果，保护最近 **40k tokens**（`PRUNE_PROTECT`）的工具调用，更早的 completed 工具输出**就地清空**（打 `time.compacted` 标记，输出变为 "[Old tool result content cleared]"）。`skill` 工具受保护不 prune。且只有当可释放量 > **20k tokens**（`PRUNE_MINIMUM`）才动手（避免频繁小改动）。注意：opencode 是**改写存储的消息**，与 pi"存储不动、只改请求视图"不同。

### 3.2 第二级：compact（LLM 摘要）

- 独立的 **compaction agent**（可配更便宜的模型）；
- 保留尾：`preserveRecentBudget` 默认 = usable 的 25%（夹在 2k–15k 之间），**按 turn 从新到旧**累加进预算；单个 turn 超预算时 `splitTurn` 在 turn 内部找切点；
- 摘要模板（`packages/core/src/session/compaction.ts` `SUMMARY_TEMPLATE`）：

```markdown
## Objective
## Important Details
## Work State (### Completed / ### Active / ### Blocked)
## Next Move
## Relevant Files
```

- **迭代更新规则**（`SUMMARY_UPDATE_INSTRUCTIONS`）写得比 pi 更明确："Carry forward objectives, constraints, user directives, decisions... even when the <conversation> does not mention them. Where they conflict, the conversation wins: state the corrected fact and drop the old claim. Move completed work from Active to Completed."
- **overflow replay**（`processCompaction`）：溢出触发的压缩后，把**最后一条真实用户消息重新 append 为新 user message**（媒体附件降级为 `[Attached ...]` 文字）——最近的用户指令逐字保留。
- **auto-continue**：自动压缩后注入合成 user 消息 "Continue if you have next steps, or stop and ask for clarification if you are unsure how to proceed."（带 `compaction_continue: true` 标记供插件区分）。
- 阈值（`overflow.ts`）：`total >= usable`，usable = context − max(output, 20k buffer)；新 core 默认 buffer 20k、keep 8k。
- 工具输出序列化给摘要器时截 2000 字符。
- 插件钩子：`experimental.session.compacting`（注入上下文/换 prompt）、`experimental.chat.messages.transform`、`experimental.compaction.autocontinue`。

### 3.3 计划文件外置

plan mode（`session/reminders.ts`）：计划写在**磁盘上的 plan 文件**里（`Session.plan` 路径）。切回 build agent 时注入合成消息 "A plan file exists at X. You should execute on the plan defined within it"。计划作为文件存在，天然跨压缩存活——和 pi 的"文件即上下文"殊途同归。

### 3.4 系统提示词：按模型家族分模板

`session/system.ts`：9 套模板（anthropic / gpt / gemini / kimi / meta / beast(gpt-4/o1/o3) / codex / trinity / default）+ `<env>`（cwd/worktree/git/平台/日期）+ project references + skills（**skill 工具懒加载**："Use the skill tool to load a skill when a task matches its description."）+ MCP instructions。注释里有句实话："the agents seem to ingest the information about skills a bit better if we present a more verbose version here and a less verbose version in tool description"。

### 3.5 context epoch（新 core 的亮点）

`packages/core/src/system-context/`：系统上下文是一组**类型化 Source**，每个 Source 有 `baseline(current)`（首次渲染）、`update(previous, current)`（变更渲染）、`removed(previous)`（移除渲染）、`load()`（观测，可返回 `unavailable` 表示暂时失败——此时**保留已批准的快照而不是构造残缺基线**）。组合后产生持久化 Snapshot（每 Source 一个 JSON 值）+ 模型可见文本；Source 变化时发出 `SessionEvent.ContextUpdated` 事件（带增量文本），而不是悄悄重写 system prompt。这是**声明式、可 diff、可持久化**的系统上下文，比 codex 的 world_state 更形式化。

### opencode 的优劣

**优**：
1. 两级治理：prune 免费、高频、不需要模型参与；compact 昂贵、低频——成本结构最合理；
2. plan 文件外置，计划状态跨压缩存活；
3. overflow replay 保住最近用户指令原文；
4. context epoch 把"系统上下文变更"做成了一等事件；
5. 摘要更新规则明确（冲突时新对话赢）。

**劣**：
1. prune 改写存储消息（人类 transcript 与模型视图会分叉，虽然 UI 有处理）；
2. 文件状态不累计（Relevant Files 靠摘要器自觉，没有 pi 的机械提取+跨代累积）;
3. 新旧两代（v1 与 core）并存，代码路径分裂，实际行为要分清哪条生效；
4. 没有存活状态快照、没有工具搜索（工具全量在 context 里）。

## 4. grok-build：全量替换 + 9 段模板 + 存活状态 reminder + 工具搜索

grok-build（xAI，本仓库 `crates/`，Rust；产品宿主 `xai-grok-shell` 不在本仓库，系统提示词组装与触发接线不可见，以下基于共享 crate 与运行体验）。它的压缩子系统 `xai-grok-compaction` 是五个里**产品化流水线最完整**的。

### 4.1 三种压缩样式

- `code_compaction`：grok-build 的**整会话 full-replace**（本节主角）；
- `intra_compaction`：Grok chat 的 per-step tail-keep；
- `inter_compaction`：Grok chat 的 turn 之间分段压缩。

### 4.2 9 段结构化摘要模板

`code_compaction/templates/full_replace_summary_prompt.txt`（即 Claude Code 那套著名 9 段格式的变体）：

```
1. Primary Request and Intent   （用户全部显式请求+意图+约束，保留 nuance）
2. Key Technical Concepts
3. Files and Code Sections      （每个文件：全路径、为何重要、相关代码；自己写的代码给完整片段）
4. Errors and Fixes             （每个错误：根因+如何修复；用户反馈逐字保留）
5. Problem Solving
6. All User Messages            （列出所有非工具结果的用户消息，按序；注明"不要把摘要指令本身算进去"）
7. Pending Tasks                （用户明确要但没做完的；"不要发明用户没要求过的任务"）
8. Current Work                 （压缩前正在做什么，具体到文件/命令/状态，"Be specific enough that work can resume mid-stream"）
9. Optional Next Step           （单一下一步；必须附最近消息的**逐字引用**"so the task is interpreted without drift"；若上任务已完成，除非明显属于既定目标，否则应问用户）
```

配套规则：
- 明确交接视角："The successor will see the user's original query plus this summary."
- **摘要链**："If earlier turns include a prior compaction summary (marked with <conversation_summary> tags...), treat it as authoritative for the early history and carry its still-relevant information forward"——跨代合并；
- 预算意识："aim for at most a few thousand words. A focused summary that fits is far more useful than an exhaustive one that gets cut off"；
- **反注入段**：提示里明确警告不要读 `/tmp/compaction/segment_*.md` 等带外记忆文件（那些是给未来 agent 的，不要现在去调工具读）——对摘要调用本身的 prompt injection 防御，细节见仁见智但很讲究。

### 4.3 压缩后的历史组装（`code_compaction/assemble.rs`）

```
[ 原始 system prompt
, user 前缀（<user_info> 等，不带 <user_query> 标签）
, AGENTS.md 重注入（user 消息；注释："re-injected verbatim so project instructions survive compaction — not dependent on the summarizer"）
, 最后一条真实用户查询（包 <user_query> 标签）
, recent messages（最后一条真实用户 turn 之后、逐字保留）
, 压缩摘要（可带 transcript hint）
, <system-reminder>（存活状态，见下） ]
```

### 4.4 存活状态 reminder（五个里独有）

`reminder.rs`：压缩后追加的 `<system-reminder>` 携带**当前世界的存活状态快照**，三个公共 section（宿主还可加 files/AGENTS.md/skills/MCP/memory 等专有 section）：

- `## Running Background Tasks`：task_id、command、状态；
- `## TODO List`：逐项带 `[pending]/[in_progress]/[completed]/[cancelled]` 标签（有未完成项才注入）；
- `## Running Subagents`：subagent_id、类型、描述、已运行秒数。

摘要管"过去"，reminder 管"现在"——接手模型不仅知道发生了什么，还知道**哪些任务还在跑、todo 到哪了**。这是对循环环节 ④ 的正面打击，其他四个 harness 都没有（codex/grok-chat 体系之外的重注入都是静态文件）。

### 4.5 工具搜索（deferred tool loading）

`xai-tool-runtime/src/search.rs`：`ToolSearchIndex` trait（BM25 / OpenSearch / 内存线性三种后端），`SearchSnapshot` 带 `total_hidden_tools`（隐藏的工具数）与 `is_ready`；搜索结果**直接带完整 input schema**（"so callers can construct dispatched tool calls without a separate schema fetch"）；`ServerSummary` 用于在 system-reminder 里列出已连接的集成。这就是本会话里 `search_tool` 工具 + 工具列表 `defer_loading` 标记的来源：大量工具（尤其 MCP）默认不进上下文，按需搜索加载。

### 4.6 工程护栏

- 阈值：`DEFAULT_AUTO_COMPACT_THRESHOLD_PERCENT = 85`（窗口百分比，grok-build 与 Grok chat 共享）；
- 独立压缩模型（`compaction_model_name`，覆盖顺序：agent 设置 > YAML > 默认常量）;
- **退化摘要检测**：`MIN_SUMMARY_SEED_CHARS = 500`（"smallest healthy prod summary observed was ~3,242 chars"），清洗后短于 500 字符视为退化，按瞬态失败重试；`max_attempts=3, retry_delay=3s, timeout=120s`；
- `select.rs`：tool-pair-safe 的尾部保留（不拆 tool call/result 对）；
- 宿主侧还有 preflight overflow、model-switch 抑制等触发接线（本仓库不可见）。

### grok-build 的优劣

**优**：
1. 交接视角显式化（"successor sees original query + summary"），9 段模板把 ②③ 全覆盖；
2. 存活状态 reminder 独有，治 ④；
3. 质量护栏（退化检测、重试、独立压缩模型、tool-pair-safe 切分）工业级；
4. 工具搜索解决工具清单侧的上下文膨胀——工具多时（MCP 场景）这是刚需。

**劣**：
1. full-replace 最激进：除尾部外全部历史丢弃，单点依赖摘要质量；摘要本身要写几千方字符，成本不小；
2. 系统提示词重（本会话可见的 ~6-7k token 工具说明书），与 pi 极简是两个极端；固定开销大的代价是每次请求都付；
3. 产品宿主闭源，关键接线（system prompt 如何组装、触发时机细节、memory/skills section）只能推断；
4. 无工具输出 spill 机制（靠输出文件路径 + 截断提示）。

## 5. deepseek-harness（dsh）：插件化、事件溯源的上下文系统

dsh（`packages/`，TypeScript，cordis 插件内核）是五个里**架构最平台化**的：上下文管理的每个部件都是独立 package + 契约 + 可换后端。

### 5.1 事件日志 + surface 双视图

`packages/core/session/src/surface.ts`：append-only session event log 是唯一事实源；**surface** 是模型可见的消息视图（user/message、assistant/message、tool/result 三类 surface 事件）。压缩在 surface 上"shadow"被替换的区间，而人类 transcript 用 append-origin 事件重建——**模型视图与人类记录彻底分离**，"replaying the session reproduces the exact conversation"（模型收到过什么）同时人类看到过什么也不丢。

### 5.2 可插拔压缩 + KV cache 对齐的摘要（五个里独有）

- `dsh-compaction`（契约）/ `dsh-compaction-basic`（默认后端）/ `dsh-command-compact`（/compact 命令）：后端可整体替换（固定模板或远程服务）；
- **KV cache 对齐**（`compaction-basic/src/summarizer.ts`，注释原话）：摘要请求**复用对话自己的 system prompt + tools + 消息前缀**，把压缩指令作为最后一条 user message 追加——"makes the auxiliary call a genuine prefix of the last routed request, so the provider's **KV cache is reused instead of invalidated**"。pi 反过来（摘要请求禁用 cache write），codex 干脆把摘要扔给服务端。dsh 是在**同一条缓存前缀上**做摘要，摘要调用几乎只付新增部分的钱；
- 8 段 checkpoint（`COMPACTION_INSTRUCTION`）：Primary Request and Intent（"quote verbatim where the exact wording matters"）/ Key Technical Concepts / Files and Code（"exact path: why it matters"）/ Errors and Fixes（"Capture user feedback and explicit instructions faithfully, especially corrections"）/ Pending Jobs / Current Work / Next Step / Critical Context；
- **CHECKPOINT_PREAMBLE**：摘要落盘为 user 消息，前缀 "This is an automatically generated checkpoint condensing an earlier span... Treat the captured context as established background and build on it without restating it. **Continue the task directly... without acknowledging this checkpoint.**"——既防止模型复述摘要，也防止它"知道"被压缩过（避免模型行为因压缩而改变）；
- 旧 checkpoint 合并规则："Do not copy it forward verbatim: preserve still-true facts, drop stale ones, and merge newer information into a single consolidated summary"；
- 每模型策略（`config.ts`）：`modelPolicies` 可按 provider/model 精确覆盖 `thresholdRatio`（默认 0.8）、`retainRatio`（默认 0.16，即保留尾部 16% 逐字）、摘要模型、重试数；
- **事务 + 稳定性检查**（`region.ts`）：摘要生成是异步的，期间对话可能继续前进；`SurfaceChangedError` 在"替换边界已不是当初构造的边界"时拒绝落地（区别于摘要器失败，手动调用方可以分别报告）；落地后有 durability checkpoint（flush）；
- `toolPairingBalancedBefore/After`：切分不拆 tool 对。

### 5.3 TokenMeter：replay-aware 的统一计量

`packages/llm/token-meter/`：从事件日志做 fold 的**重放感知**计量服务，compaction、占用率显示、telemetry 共享同一套账（不依赖压缩引擎本身）；纯启发式（文本）+ 适配器声明的视觉 token 定价；"reuses provider-reported usage **only when the request envelope matches exactly**"——前缀没变才信 provider 的 usage，否则自己算。压缩决策、UI 显示、埋点三者口径一致，这在其他 harness 里都不是显式保证。

### 5.4 工具结果治理：pruner + spill 两件套

- `dsh-compaction-tool-result-pruner`：**无模型**的确定性 head/middle/tail 修剪（`thresholdChars/headChars/tailChars` + `PRUNE_MARKER`），并为每个被剪节点记录 shadow-price 事件给 TokenMeter 用；
- **spill 家族**（`spill/`、`spill-local/`、`spill-policy/`）：工具输出超过 `maxInlineBytes` 时，全文存入 spill artifact（session 范围的本地文件），模型看到**有界预览 + locator（可后续 read/grep 的位置）**。"keeps oversized tool output out of the model's context **without losing it**"——这是四个环节里 ① 的最优雅解法：数据不丢、上下文有界、可召回。pi 的截断是"丢了就丢了"，dsh 是"挪走了还能拿回来"。

### 5.5 持久化状态：goal / todo / plan

- `goal/`：**每会话一个持久 goal**，存活于 session log（跨 restart/resume/fork），模型工具 `get_goal/create_goal/update_goal` + 人类 `/goal` 命令 + `goal-round-driver`（把活跃 goal 变成自动续跑的轮次）。"Goal state lives in the session log, so nothing in the group keeps a separate store."
- `todo/`：`todo_write` 工具，整表替换，跨 turn 与重启持久；
- `plan/`：plan mode（探索设计 → 审批 → 执行）。

### 5.6 指令文件的字节预算 + 变更追踪

`context/agent-instructions/src/render.ts`：CLAUDE.md/AGENTS.md 类指令在**显式字节预算内渲染**（UTF-8 安全截断、记录 omitted/truncated 清单，"Workspace instructions were omitted or truncated to fit the configured byte budget"）；变更追踪（`AgentInstructionChange {action: set|replace|remove, scope, path, digest}`）：指令变化时注入 "This complete workspace instruction baseline **replaces all earlier** workspace instruction baselines" 的替代基线消息，动态状态存在模型可见提示词之外。

### 5.7 跨会话引用

`context/session-reference/`：`@label` 提到其他会话 → 解析为**有界、只读、不可信**的快照作为背景上下文，带固定警告（禁止服从快照内的指令/权限声明/工具请求）。跨会话记忆注入的注入防御做成了规范。

### dsh 的优劣

**优**：
1. 每个部件是契约+后端，可替换、可测、可组合——五个里工程抽象最干净；
2. KV cache 对齐的摘要，摘要成本最低；
3. spill 把"大输出"从"丢失"变成"召回"；
4. TokenMeter 统一计量口径（压缩决策/UI/telemetry 一致）；
5. goal/todo 持久化在事件日志里，状态外置做得彻底；
6. surface/log 分离，模型视图与人类 transcript 互不污染；
7. 摘要落地的事务性（边界漂移检测）考虑了真实竞态。

**劣**：
1. 架构最重：理解成本、集成成本都高（70+ 个 package）；
2. 摘要器是 one-shot 整段（shadow 区间一次摘要），没有 pi 的 split-turn 细分结构，超长单 turn 场景弱一些；
3. 新秀，无公开生产战绩，checkpoint 模板与 85%/16% 默认值的实际效果未经大规模验证；
4. 没有 codex 式的"原文 user message 全保留"（user 消息进摘要走 8 段模板）。

## 7. 设计哲学归类

五个 harness 其实站在三个不同位置：

1. **pi：上下文最小主义**。相信"磁盘是免费的，窗口是贵的"，把上下文当作**指针集合**，知识按需拉取；压缩是**状态交接文档**的维护。代价：对模型自主性要求最高，弱模型吃亏。
2. **codex / grok-build：交接工程化**。把压缩当**产品功能**做：模板、护栏、重试、降级、重注入、快照，全流水线。codex 偏"保留原文"（user message 全留），grok-build 偏"摘要即世界"（full-replace + 状态 reminder）。
3. **opencode / dsh：治理平台化**。把上下文当**有预算的系统资源**管理：prune/spill/字节预算/token 计量/契约化后端。dsh 走得更远，做到事件溯源级别的严谨。

对"9 小时循环"的治愈力排序（主观，针对②③④）：**grok-build ≈ dsh > codex > pi > opencode**。pi 的 ③ 解法（文件清单）独树一帜但 ④ 缺失；codex 的 ② 解法（原文保留）最稳但 ③④ 缺失；grok-build 是唯二全覆盖的；dsh 靠 spill+goal/todo+模板全覆盖但依赖架构完整落地。

**一个值得注意的收敛**：pi（2025）、codex、opencode、grok-build、dsh 五个独立团队的摘要模板在 2026 年收敛到了几乎同构的形状——`目标/意图 + 约束 + 进度(完成/进行中/阻塞) + 决策 + 下一步 + 关键上下文 + 文件清单`。这说明"结构化 checkpoint"已经是事实标准，**差异不在模板，而在：模板之外机械保留什么（原文消息？文件清单？存活状态？）、以及压缩前后的重注入策略**。

## 8. 对 ruyishell 的启示

### 8.1 ruyishell 现状盘点（`internal/agent/`）

已有：
- **L1 折叠**（`collapse.go` `CollapseOldTools`）：请求视图里最近 64KB 的工具输出保留原文，更早的折成一行占位符；turn 本身不动；
- **L2 自检提示**（`engine.go`）：上下文到 75% 或 ~144k tokens 时注入 `[rysh 自我检查]`，**让模型自己**重写 todo、丢弃陈旧细节；
- **mission 锚点**：第一条用户消息作为使命，系统提示词要求"上下文只保留使命、todo、子任务状态"；
- **manager/worker 架构**：子任务上下文不进入 manager，只回传 ≤500 字报告；
- 系统提示词里有完整的上下文纪律条款。

对照循环四环节，缺口很清楚：

| 环节 | 现状 | 缺口 |
|---|---|---|
| ① 变重 | 无源头截断（工具输出全量进 turn），L1 折叠是事后补救 | 源头截断 / spill |
| ② 忘目标 | L2 是"让模型自己整理"，无 LLM 结构化压缩 | **没有真正的 L2 压缩** |
| ③ 重读 | L1 占位符只有命令+exit code，"为什么跑"丢了 | 无文件状态累积 |
| ④ 又重 | 无存活状态快照 | todo/jobs/子任务不重注入 |

**最致命的是 ②**：当前 L2 的"自我检查"是让当事人自己当法官——上下文已经很重、模型已经接近失焦的时候，指望它"整理上下文"本身就是不可靠的。9 小时循环里"压缩"实际发生的是 L1 折叠：占位符把语义删干净了，模型只能靠重读文件重建认知，重建的输出又把上下文撑重——闭环就此形成。

### 8.2 建议（按收益/成本排序）

**P0 — 引入结构化 checkpoint 压缩（真正的 L2）**

这是单点收益最大的一项，直接对治 ②③。照抄事实标准模板即可（五家收敛的形状）：

```
## 目标（Goal）        —— 用户要什么，逐字引用关键约束
## 约束与偏好
## 进度：已完成 / 进行中 / 阻塞
## 关键决策
## 下一步
## 关键上下文
## 已读文件 / 已改文件   —— 机械提取，不靠模型回忆
```

要点（全部有出处）：
- 触发：`estimatedTokens > window * 0.85`（grok-build/dsh 的 85%/0.8）而非现在的固定 144k；window 按模型配置；
- 保留尾部：`keepRecentTokens` 2k–15k 或窗口的 16–25%，**按 turn 边界切，永不拆 tool call/result 对**（五家共识）；
- **迭代更新**：第二次压缩把旧 checkpoint 传给摘要器，规则 "保留目标、In Progress→Done、丢弃已失效信息"（pi/opencode/dsh 都有，dsh 的措辞最可抄）；
- 摘要落位：作为 user 消息注入，带前缀说明（"以下 checkpoint 概括了之前的对话，直接继续任务，不要复述"，抄 dsh CHECKPOINT_PREAMBLE）；**摘要放在最近保留消息之前**；
- 摘要请求尽量复用原 system prompt + tools 前缀（dsh 的 KV 对齐，省一次全量 prefill）；
- 摘要质量护栏：输出过短（<500 字符）视为退化重试（grok-build）。

**P1 — 压缩后重注入（对治 ②④）**

压缩后按固定顺序重注入（grok-build assemble 的顺序已验证）：
1. 项目指令（ruyishell 的 AGENTS.md/CLAUDE.md 支持）；
2. **mission**（第一条用户消息原文——ruyishell 系统提示词已把它定为锚点，现在压缩后真的把它放回上下文里）；
3. **todo 清单**（`tools_todo.go` 已有状态，渲染成 `[pending]/[in_progress]/[completed]` 列表——grok-build reminder 格式）;
4. **存活子任务与后台 job 快照**（task id、prompt 摘要、状态、job id/命令/状态——ruyishell 已有 jobs 子系统，渲染成本极低）。

这一段可以做成一个纯函数 `RenderStateSnapshot(todo, tasks, jobs) string`，压缩后作为 `<system-reminder>` 追加。**摘要管过去，快照管现在**——这是 ruyishell manager/worker 架构下最便宜的一条"防漂移+防重读"双保险。

**P2 — 文件状态累积（对治 ③，pi 的独门解法）**

维护 session 级 `readFiles/modifiedFiles` 集合：
- 每次 read/edit/write 工具执行时追加（manager 和 worker 各自维护）;
- checkpoint 的 `## 已读文件/已改文件` 段由 harness 机械渲染（不是让摘要器从对话里回忆——回忆会漏、会编）；
- 跨代累积：新 checkpoint 合并旧 checkpoint 的清单（pi `extractFileOperations` 做法）；
- worker 报告里把"读过/改过哪些文件"作为结构化字段回传，manager 汇总。

**P3 — 工具输出源头治理（对治 ①）**

- 源头截断：read 默认保头（2000 行/50KB）、bash 保尾，截断时附 "原始 N 行/总 M KB，已截断"（pi 的做法，占位符要带元数据让模型知道丢了什么）;
- **spill**：超过阈值（如 100KB）的输出写 `~/.rysh/spill/<session>/<n>.txt`，上下文里放"前 50 行预览 + 文件路径 + 提示可用 read 读取"（dsh 的做法）。ruyishell 是 shell，写文件是零成本操作，这是终端形态的天然优势——比 pi 的"截断即丢失"强一档。

**P4 — 计量与纪律**

- token 估算统一：provider usage 为锚 + 尾部 char/4（pi 做法，中文按 char/2 更稳可测）；替代现在 `selfCheckL2Est=144000` 的固定值；
- 现有 L1 折叠保留，但占位符升级：`[已折叠] read internal/agent/engine.go（12k chars，exit 0）` → 改为引用 spill 路径（若已 spill），与 P3 联动；
- 系统提示词里的"上下文纪律"可以瘦身——纪律交给机制（checkpoint+快照），提示词只留一句"上下文可能已被 checkpoint 压缩，以 todo 与快照为准"。现在的长纪律条款在模型失焦时恰恰是最先被忽略的内容。

**不建议照搬的**：
- codex 的"全部 user message 保留"——ruyishell 的 mission 锚点已经覆盖核心诉求，全量保留成本高收益边际小；
- pi 的极简系统提示词——ruyishell 的模型组合里若有弱模型，grok-build 式的显式工具说明书更稳；可折中为"常用工具详写、低频工具一行+按需展开"；
- dsh 的全套事件溯源架构——ruyishell 当前规模下过度设计，但 **surface/log 分离的思想**（模型视图 vs 人类 transcript）值得在下次重构会话存储时引入。

### 8.3 核心状态模型：rysh 该记住什么（设计决策，2026-08-28）

manager 的上下文只保留一份**核心状态**，其形状就是 checkpoint 模板本身：

| 核心状态（rysh 的上下文只装这些） | 不进入 rysh 上下文（子智能体自己消化） |
|---|---|
| 使命（第一条用户消息原文） | 每一步具体怎么做 |
| todo：进度（完成/进行中/阻塞） | 调用哪些工具、工具的返回 |
| 关键决策及其理由 | 工具如何组合、中间探索过程 |
| 文件清单：**已改/交付**的文件为主（产物归属），报告点名的关键文件为辅 | 大段文件内容（子任务自己 read） |
| 子智能体状态：task id、目标摘要、状态、最近一次报告的结论 | 子任务的完整 transcript |

判断一条信息该不该进 manager 上下文的准则：**接手这个 session 的新模型，为了继续推进，是否必须不用重推就能用上它？**"是什么/到哪了/改了什么/谁在跑"必须直接在场；"怎么做的"可以重推（子智能体拿到简报后自己从文件重建认知），所以可以丢——这正是它可被压缩掉的资格。

三个配套约束：

1. **报告是核心状态的增量单元**。worker 报告三段（已完成/关键发现与改动/未完成与下一步）恰好是核心状态在单个子任务粒度上的 delta——manager 验收后把 delta 合并进 todo 与文件清单，核心状态就始终完整。报告的 500 字上限是"how 不污染"的执行手段。
2. **模板递归适用**。子智能体自己的上下文膨胀时，用同一套模板做自己的 checkpoint——"how"活在子任务那一级，manager 那一级只吸收其报告。同一形状、两层粒度。
3. **验收抽查是 manager 唯一合法的亲自工具使用**，且必须有界（跑相关测试、看 diff、读改动片段），抽查输出本身也要小——否则 manager 又会通过"验收"这个口子把过程细节漏回上下文。

### 8.4 落地顺序建议

1. P0 的 checkpoint 压缩 + P1 的重注入（一个 PR，~500 行 Go，直接打断 9 小时循环）；
2. P2 文件清单 + worker 报告结构化（小改）；
3. P3 源头截断 + spill（中等，改 tools 层）;
4. P4 计量统一 + 提示词瘦身（收尾）。

每项都可以用"长跑任务 + 注入大输出"做回归：验证压缩后模型不再重读已读文件（看 read 调用去重率）、不再重述任务（看下一句动作是否与 todo 一致）、循环不复发（看压缩次数与总时长）。
