# 技术选型调研

> 调研目的：为 ruyishell（以 shell 为默认、AI 为副驾的交互式 AI shell）在 **Rust / Go / Zig** 三种候选语言间做生态事实核查。
> 数据来源：GitHub REST API（`https://api.github.com`）。**本文件内所有 star 数、归档状态、最近提交日期均为 2026-08-24 实际从 GitHub API 取回的数据**，每条附来源 URL。标注"已知事实"的条目为业界普遍认知，非本次联网查证。
> 备注：本次调研环境外网仅通 `api.github.com` 与 `pkg.go.dev`；GitHub 未认证限额约 60 次/小时，本次共使用约 20 次查询。

## 1. 背景与结论

ruyishell 的核心诉求：PTY 处理（master/slave、信号转发）、高要求 TUI、多模型 provider 客户端、agent loop 流式输出、静态单文件二进制分发。

**结论先行（2026-08-24 最终决策）**：

**ruyishell 实现语言选定 Go**（原"实现语言：Rust"的初稿决策已更新，见 [架构设计](./架构设计.md) ADR-3）。依据：

- **Go 是三条路线里"官方 SDK + 成熟生态"最全的**：OpenAI 与 Anthropic 均有官方 Go SDK（openai-go 3,425★、anthropic-sdk-go 1,180★，皆活跃）；社区 OpenAI 客户端 go-openai 10,742★；TUI 生态 bubbletea 44,511★ + lipgloss 11,741★ + bubbles 8,830★（皆活跃）；PTY 库 creack/pty 2,078★（另有 aymanbagabas/go-pty 活跃维护）。
- **Rust 生态整体活跃，但有一处关键减分**：官方 Anthropic Rust SDK **不存在**（`anthropics/anthropic-sdk-rust` 404 查证），需走社区 crate 或兼容网关；其 TUI（ratatui 22,345★）与 PTY（portable-pty，wezterm 28,513★ 未归档）均活跃维护。
- **Zig 的 TUI 生态明显偏弱**：最成熟的 TUI 库 libvaxis 约 2k★（而 ratatui 22k★、bubbletea 44k★），且官方 SDK 体系（OpenAI/Anthropic）在 Zig 下几乎空白。ziglang/zig 本体已迁往 Codeberg（GitHub 描述即 "Moved to Codeberg"）。
- **决定性因素**：除上述生态事实外，团队对 Go 更熟、Go 静态单文件交叉编译为语言内置能力，迭代更快。

## 3. 关键发现

### 3.1 wezterm **未被归档**（重要修正）
任务假设 wezterm/wezterm 可能已归档。**实查 `archived: false`**，28,513★，最后提交 2026-08-23（查证日当天）。仓库内 `pty/` 目录（portable-pty crate）仍随主项目维护（已核实存在 `Cargo.toml`、`src/`、`examples/`）。**结论：文档无需为 portable-pty 提供替代方案，它仍是被活跃维护的 PTY 库**；只是 portable-pty 的发布节奏与版本号跟随 wezterm，这是使用上的注意点，而非维护问题。

### 3.2 Anthropic 官方 SDK 只在 Go/Python/TS 等语言，**没有 Rust**
- `anthropics/anthropic-sdk-rust` → GitHub API **404**（仓库不存在）。
- 查证 `user:anthropics` 组织内 SDK：`anthropic-sdk-python` 3,848★、`anthropic-sdk-typescript` 2,095★、`anthropic-sdk-go` 1,180★，**无 Rust SDK**。
- **对 Rust 的影响**：ruyishell 若走 Rust，Anthropic provider 需用社区 crate 或经 OpenAI 兼容网关/代理（如本地 llama-server 的 Anthropic 兼容端点）。这是本调研对现有架构文档（"Rust 有多模型 provider 库"）最需要补强的一点。
- **选型后果（2026-08-24）**：ruyishell 已选定 Go，该问题随之消失——Anthropic 直接走官方 `anthropics/anthropic-sdk-go`。
- **对 Go 的影响**：Go 是唯一"OpenAI + Anthropic 官方 SDK 同时存在且都活跃"的路线。

### 3.3 Zig 现状：语言本体迁走，TUI 生态小而活跃
- **ziglang/zig 本体**：43,299★，`archived: false` 但描述为 **"Moved to Codeberg"**，GitHub 最后提交停在 2025-11-27 → 开发主阵地已迁往 Codeberg，GitHub 仓库处于镜像/收尾状态。若要跟进 Zig 版本与 issue，需到 Codeberg。
- **Zig TUI 生态**（按 star 排序，均查证 2026-08-24）：
  - `rockorager/libvaxis` 1,974★（未归档，2026-08-20 活跃）——当前 Zig 头号 TUI 库；
  - `meszmate/zigzag` 527★（未归档，2026-08-14 活跃）；
  - `akarpovskii/tuile` 218★（**已归档**，archived: true）；
  - 衍生证明：`neurocyte/flow` 终端编辑器 2,183★、`fairyglade/ly` 显示管理器 7,534★。
- **Zig 终端能力的上限由 Ghostty 证明**：`ghostty-org/ghostty`（原 `mitchellh/ghostty` 已 404，迁至 ghostty-org）60,114★，2026-08-24 仍活跃。这说明"Zig 做高性能终端"可行，但那是终端模拟器级工程，**不等于有现成的 TUI 框架/PTY 库供 ruyishell 直接复用**。

### 3.6 静态分发便利度（已知事实，非本次联网查证）
- **Go**：交叉编译 = 设 `GOOS`/`GOARCH`，`CGO_ENABLED=0` 默认产静态单文件，体验最顺。
- **Rust**：交叉编译需自备 target + 链接器；静态需 musl target（体积会更大），可行但要配置。
- **Zig**：`zig build-exe -target` 自带 libc 与交叉编译能力，静态单文件是第一公民用法，体验最顺。
- 按 ruyishell"交互体验优先、体积不是重点"的定位（架构设计 ADR-3），三者均满足分发需求，差距不足以改变语言选型。

### 3.10 Rust 跨平台 PTY 库调研（补充，2026-08-24）

> 调研问题：Rust 有没有同时处理 Windows / Linux / macOS 的成熟 PTY 库？
> **结论：有，唯一主流选择是 `portable-pty`**（wezterm 作者 Wez Furlong 维护、随 wezterm 仓库发布）。它是 Rust 生态中唯一"三平台统一且被生产级终端验证"的 PTY 库；其余候选要么仅 Unix、要么仅 Windows，或体量过小。

**portable-pty 事实核查（2026-08-24，crates.io / GitHub / docs.rs 实测）**：
- crates.io：`portable-pty` 最新 0.9.0（2025-02-11 发布，未 yanked），MIT；总下载 12,418,146，近 90 天下载 5,934,445；**反向依赖 499 个**；描述即 "Cross platform pty interface"。
- 源码跨平台后端（wezterm 仓库 `pty/src`，main 分支实查）：
  - Unix（含 macOS）：`unix.rs` 用 `libc::openpty`，子进程 `setsid()` 成为会话/进程组组长（`cfg(unix)` → Linux/macOS/BSD 通用）。
  - Windows：`win/conpty.rs` 的 `ConPtySystem`，基于 **ConPTY**（动态加载 `CreatePseudoConsole` / `ResizePseudoConsole` / `ClosePseudoConsole`，见 `psuedocon.rs`），`CreateProcess` 启动子进程。
  - 一行取当前平台实现：`native_pty_system()`；`pub type NativePtySystem` = unix `UnixPtySystem` / windows `ConPtySystem`。
- 与 ruyishell 需求的对应（master/slave + 信号转发）：
  - `PtySystem::openpty()` → `PtyPair { master, slave }`；`slave.spawn_command(CommandBuilder)` 起子进程。
  - `MasterPty` trait 提供 `resize()`、`process_group_leader()`（Unix 上为 `tcgetpgrp` 当前前台进程组 → 信号转发入口）、`kill()`（三平台均有）。
- 生产验证：wezterm 本体 `Cargo.toml` 即 `portable-pty = { path = "pty" }`（实查）——WezTerm 是 Windows/Linux/macOS 三平台生产级终端，**Windows 的 ConPTY 路径同属生产级**。
- 维护活跃（GitHub 实查）：仓库未归档、2026-08-23 仍在提交；近期 pty 提交 2026-08-18（filedescriptor 迁 windows-sys）、2026-06-07（"pty: windows: fix kill()"）→ 含 Windows 侧持续修复。
- **本机实测（Linux，2026-08-24）**：`cargo add portable-pty` + 编译通过；实测经 pty 起交互式 bash——echo 回显、`resize()` 无错、`process_group_leader()` 返回前台 pgid、向该 pgid 发 SIGTERM 成功终止前台 `sleep 30`（bash 打印 "Terminated"）、`child.wait()` 正常。

**使用注意点**：
- 发布节奏慢：crates.io 最新 0.9.0 为 2025-02-11，其后修复走 git 依赖：`portable-pty = { git = "https://github.com/wezterm/wezterm" }`。
- 同步 API，无内置 async/tokio：features 仅 `serde_support`；异步需自行包 master fd（Unix 用 `tokio::io::unix::AsyncFd` 等），wezterm 自身在线程里做非阻塞 I/O。

### 3.11 Rust（portable-pty）与 Go（creack/pty + go-pty）PTY 实现成熟度对比（2026-08-24）

> 承接 3.10：ruyishell 选型在"同一架构思路"（Unix pty + Windows ConPTY）下，Rust 侧为 `portable-pty`，Go 侧为 `aymanbagabas/go-pty`（Unix 底层即 `creack/pty`）。本节逐维对比两者成熟度。

| 维度 | Rust：`portable-pty` | Go：`go-pty`（Unix 底层 `creack/pty`） |
|---|---|---|
| 诞生时间 | 2019-05（crates.io 0.1.0 发布，共 11 个版本） | go-pty：2023-07；creack/pty：2011-05 |
| 定位 | 功能完整的 PTY 库（PtySystem / CommandBuilder / Master/Slave 抽象） | 薄封装：`Pty` / `Cmd`；Unix 直接委托 creack/pty |
| 采用规模 | crates.io 总下载 1241 万、近 90 天 593 万、反向依赖 499 | creack/pty ★2,078、readme 引用 434 个仓库；go-pty ★81 |
| 平台与后端 | Unix `libc::openpty` + Windows ConPTY；`native_pty_system()` 运行时取平台实现 | Unix 走 creack/pty（POSIX）+ Windows ConPTY（`x/sys/windows.CreatePseudoConsole`）；编译期 `//go:build` 分支 |
| 生产验证 | **WezTerm 三平台生产终端**直接依赖，Windows ConPTY 路径同为生产级 | creack/pty 被大量项目使用（Unix 侧久经考验）；go-pty 的 Windows ConPTY 侧生产用例相对少 |
| 维护活跃度 | wezterm 仓库内维护，2026-08-18 仍有提交（含 Windows 修复）；crates.io 发布慢（0.9.0 停在 2025-02-11） | go-pty 2026-08-17 更新（以依赖 bump 为主）、三平台 CI 含 `go test -race`；creack/pty 2026-06-01 更新、v1.1.24 |
| 版本/API 稳定 | 0.x 系列，跨版本存在破坏性改动（0.6→0.7→0.8→0.9） | creack/pty v1.x 稳定；go-pty v0.x 但 API 面很小、变化少 |
| 异步模型 | 同步 API、无内置 async；异步需自行包 master fd（如 `tokio::io::unix::AsyncFd`） | Go 中 master 即 `*os.File`，天然配合 goroutine；bubbletea 可直接消费 |
| 额外能力 | 现成 `kill()`、`process_group_leader()`（信号转发）、termios、tty_name、shell-words 命令行解析 | SSH terminal modes 支持（x/crypto/ssh 集成）；信号转发需自行对 master fd 做 tcgetpgrp |

数据来源（2026-08-24）：crates.io `portable-pty`（下载/版本/反向依赖）、`api.github.com/repos/aymanbagabas/go-pty`、`.../creack/pty`（创建时间/star/提交）、`api.github.com/search/repositories?q="creack/pty" in:readme`（434 个仓库）、go-pty 源码 `pty_unix.go`/`pty_windows.go`/`ssh.go` 与 `.github/workflows/build.yml`（三平台矩阵 + -race）、`proxy.golang.org`（版本列表）、wezterm `.github/workflows`（含 `gen_windows*.yml`）。

**结论（平衡判断）**：
- 两者成熟度**总体相当、各有侧重**，且同为"Unix pty + Windows ConPTY"设计，选型不构成风险。
- **Go 侧优势**：Unix 主干 creack/pty 有 15 年历史、是 Go 生态事实标准（434 仓库引用、v1.x 稳定）；go-pty 三平台 CI 带 `-race`；Go 的 goroutine 模型让 PTY 与 TUI（bubbletea）对接最顺。
- **Rust 侧优势**：portable-pty 功能更全（进程组/信号/kill/termios 均为现成 API），Windows ConPTY 路径经 WezTerm 三平台生产验证；短板是 crates.io 发布慢、0.x 有破坏性改动、异步需自己包 fd。
- **对 ruyishell 的影响**：维持 Go 选型不变（架构设计 ADR-3、ADR-6）。若未来某组件引入 Rust，portable-pty 完全够用，两者可互换而不构成能力缺口。

## 4. 建议（最终决策）

1. **实现语言选定 Go**（[架构设计](./架构设计.md) ADR-3 已更新）：TUI 不引入 bubbletea 之类的全量渲染框架，采用"透传共享屏 + 一屏一流"直接写 ANSI/PTY 字节流（见 ADR-7，修订原 Route C 的 alt-screen 全量视图）；PTY 三平台统一用 `aymanbagabas/go-pty`（Unix 底层即 creack/pty、Windows 走 ConPTY，见 [架构设计](./架构设计.md) ADR-6）；配置解析用成熟 TOML 库。
2. **Provider 用内置 OpenAI 兼容 SSE 客户端**（见架构设计 3.5）：`internal/provider` 直接对接各家 `/chat/completions` 与 `reasoning_content` 扩展，改 base_url 即可切换 Grok / Mistral / 本地 llama-server / 通义 / GLM / DeepSeek / Kimi 等；不引入官方 SDK，避免第三方依赖漂移。
3. **不建议切 Zig**：Zig TUI 生态头号库 star 仅约为 ratatui/bubbletea 的 1/10，官方 provider SDK 空白，语言本体还迁去了 Codeberg；Zig 的静态分发优势不足以覆盖这些缺口。
4. **静态分发**：`CGO_ENABLED=0` 交叉编译单文件，安装脚本按目标平台出产物。
